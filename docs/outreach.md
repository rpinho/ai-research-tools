# Outreach: draft, lint, approve, send

The outreach module never sends or fetches a message. It records a local lifecycle: draft, lint, approve, sent, reply, close or drop. Sending belongs to a separate tool and requires the operator's authorization for the actual message.

Set `RH_CONTACTS` to a private JSON file containing an array of objects with a nonempty `name` string. Names must be unique ignoring case. An optional `language` field holds the recipient's language as a code such as `pt`; unset or `en` means English and changes nothing. Extra fields may hold addresses for your separate sending tool; the harness uses names and that one field. Nothing in this repo contains contacts. Do not commit that file. Ledger metadata rejects email-address-shaped strings; draft bodies remain private files.

Set `RH_VOICE_COMMAND` to a shell-quoted executable and arguments. It receives the draft on stdin; lines starting `FAIL:` or a nonzero exit refuse lint. It is executed as an argument vector without a shell. For a social reply, the harness appends `--reply`. A missing checker refuses. No personal voice policy is provided. The tiny checker under tests is a synthetic fixture, not a writing standard.

`OUTREACH.toml` sets question limits and follow-up timing. Optional `science_checks = true` invokes `RH_SCIENCE_CHECK_COMMAND`, which receives JSON with `text`, `language` and `attachments` on stdin and uses the same failure convention. That replaces an installation-specific Python import. A checker that ignores `language` is unaffected by its arrival.

**Two-language email.** When a recipient's `language` is not English, that language is the default for the whole email, and the email opens and closes in it. English is required only where the content is technical: numbers, variables, equations, methods, measurements. Attachments are always English. The rule holds even for a recipient who writes their own science in English. Lint fails a technical paragraph in the recipient's language, an opening or closing that is not in it, and an attachment that is not English; ordinary prose in English anywhere is a warning, because it belongs in their language too. A paragraph counts as technical when it carries a maths symbol, a variable-like token, a statistical acronym, a measured number (a decimal, or a number with an abbreviated unit such as `7 s`), a run of three or more bare numbers, or a dense run of distinct technical terms. Counted numbers are not measurements: a year ("I left in 2009"), a duration in words ("four years ago", "thanks for the 20 minutes"), a numbered reference ("Remark 4.2", "Table 3"), a link and the European Portuguese intensifier "100%" are all ignored. Neither is the vocabulary alone enough ("a separate model re-checked the result" is prose), and a term repeated, as in "data science and data engineering", counts once.

**Independent re-check and pod-touched evidence.** Two gates, from the friends-lane postmortem (Ricardo, 11-05). A draft names the claim directories it reports with `--claim DIR`, and lint fails when a claim has no recorded independent re-check (`RECHECK_MISSING`), when the re-run did not reproduce it (`RECHECK_FAILED`), when the re-check dropped it (`RECHECK_DROPPED`), or when evidence produced on a pod was last re-checked before the configured host incident (`POD_EVIDENCE_STALE`); `CLAIMS_REQUIRED`, `CLAIM_MISSING` and `RECHECK_LEDGER_MISSING` cover a missing claim, directory or ledger, and `POD_EVIDENCE_UNDATED` warns when pod evidence has no incident to be dated against. Both read one artifact the lane already writes: `RECHECK.csv` in a re-check root, one row per claim, with the claim's directory name in `id`, the independent re-run's outcome in `rerun` and the re-check's own verdict in `verdict`; an optional `utc`, `date` or `checked_utc` column dates a row, and the ledger's mtime dates it otherwise. A claim counts as pod-touched when its directory holds entries named `pod_*` or `pod-*`, which is deliberately generous: a leftover pod script is answered by a re-check after the incident. Configure in the lane's `OUTREACH.toml`: `recheck_roots` (a list of directories or globs), optional `pod_incident_utc` (without it, pod-touched evidence only warns, since an installation with no incident has nothing to re-run after) and optional `require_claims = true` (a lane whose emails always report results). A misconfigured value is refused rather than quietly disabling the gate, and `claims` also reaches `RH_SCIENCE_CHECK_COMMAND` in its JSON payload. [claim_evidence.py](../harness/claim_evidence.py).

**No infrastructure or operations in a message to a person (Ricardo, 11-06).** A message to a friend carries only what the friend needs; our provider, our pods, a security incident, a key rotation, the harness and its watchdogs, and why something was re-run are none of them. The rule came from one sentence in an email of 11-05 — "The first two ran on a RunPod server that has since had a security incident" — which the recipient wrote back to ask about: it cost a round trip, moved the subject from the result to our plumbing, and reported a host compromise he had no way to act on. Lint fails any non-public message (email, `x_dm`, `linkedin`) carrying one of those terms, as `OPS_DETAIL: <term>`; a public post is not covered, because naming one's own tools and hosts in public is a different decision. The vocabulary is deliberately narrow, because these are working scientists and several ops words are ordinary words in their fields: bare `incident` is an incident wave, `lane` is a traffic lane, `compromised` is a compromised cell line, `modal` is a modal split, and `key` is a key result. So it matches provider names, unambiguous ops nouns and multi-word phrases (`security incident`, `key rotation`, `server crashed`) rather than their component words, and two ambiguous words are checked with their sentence for company: `pod` fails beside rented-machine or incident wording and not in "each seed pod holds four to six ovules", and an agent's name (`codex`, `claude code`) fails only beside incident wording, since the tool that did the work is part of the story. When the recipient raised the subject themselves, `rh outreach draft --asked-about TERM` drops that one term to a warning so a reply can answer them; it takes a term from the check's own list, so a typo cannot quietly turn the check off and the ledger records our word for the subject rather than the recipient's wording. Only the matched term is ever reported, never the surrounding text. `ops_mentions.terms(text)` returns those term names as a set, for a caller that wants to decide for itself — running it over an incoming message and passing what it finds as `asked_about` is how a lane with the recipient's own text in hand can exempt what they raised, without parsing a failure message. [ops_mentions.py](../harness/ops_mentions.py).

Language identification is a small offline heuristic over function words and letters English does not use, currently covering Portuguese against English ([mixed_language.py](../harness/mixed_language.py)). It never touches the network and never loads a model. When a passage is too short or too mixed to call, it reports nothing rather than blocking a send; short openings and closings are decided by their greeting words instead. It reports paragraph positions, never the text, so the lane ledger holds no part of a private draft.

Lint checks question count, links, recent contact collisions and similarity across drafts. It normalizes names, links and titles; first/last sentence word-set Jaccard thresholds are 0.6 and body 5-gram Jaccard is 0.35. Similarity is reported as a **warning** and never fails a draft: two emails sharing a conventional greeting or sign-off is normal, and the two-language rule above makes a shared sign-off likelier still. The voice check is what guards against a templated message. These heuristics can miss templated spam or flag legitimate messages. A documented collision override is possible, and `sent --utc` records a message that went out before the ledger caught up.

**A message that already went out.** `sent --utc` records a send the ledger caught up with late, but it still needs an approved draft, and approval still needs a lint PASS — so a message that already left and whose text fails today's lint could not be recorded at all. On 11-05 that cost a thread its record: the row had to be dropped, and the friend's reply had nothing to attach to. `record-sent ID --message-id M --via api --utc WHEN --reason WHY` records it anyway. Lint still runs and every finding is kept on the row under `recorded_after_the_fact` (`lint_ok`, `findings`, the operator's `reason`), as warnings rather than a refusal; the follow-up falls due from the real send time, and `reply` can attach to it. It is bookkeeping, never authorization: the row gets no `approval`, and the send hook matches submitted bytes against an approved entry only, so a recorded row can never authorize a send. It refuses a future `--utc`, a row already recorded as sent, and an approved draft (which belongs in `sent`), and `approve` still refuses the row afterwards.

Approval requires a current passing lint hash and the operator's approval quote. Any byte change invalidates approval. `sent` requires matching approved bytes and records a message identifier; follow-ups become due after the configured interval. The optional email hook checks exact submitted bytes against the latest approved ledger entry. Approval enforcement defaults to warning; set `RH_OUTREACH_GATE=enforce` in the sending environment. Voice failures deny in both modes. The hook cannot authenticate the person behind an approval quote and matches message bodies, not recipient authorization.
